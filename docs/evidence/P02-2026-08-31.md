## Governing numerical inventory

The model stores `startValue` and `increment` as single precision and performs an explicit dependent
loop:

```text
x_(k+1) = fl_single(x_k + h)
reference change at k = k * double(stored h)
step error at k = double(stored x_(k+1)) - double(stored x_k) - double(stored h)
signed error at k+1 = signed error at k + step error at k
```

Recursively accumulated error coordinates prevent either a tiny update or a tiny starting value
from disappearing inside a large binary64 subtraction. The observed change trace is a display sum;
`referenceChange` and `cumulativeError` retain the governing two-part result. The retained cases are:

- baseline: `x_0=1`, `h=3*2^-25`, 64 additions; expected change 48 starting ULPs, observed change 64 ULPs, signed error +16 ULPs;
- exact limit: one-ULP/eight-ULP updates accumulate without error while spacing remains fixed;
- absorbed limit: `x_0=1`, `h=2^-25`; every 0.25-ULP update is lost;
- scale sweep: fixed `h=3*2^-25` is three ULPs at 0.25, 0.75 ULP at one, and below half an ULP at four and sixteen;
- update sweep: 0.25, 0.75, 1, 1.25, and 1.75 ULP at one, deliberately avoiding exact half-ULP ties;
- broken grouping case: 1024 ordered 0.25-ULP updates leave one unchanged, while one grouped update rounds to `1 + 256*2^-23`;
- reference-loss limit: at `x_0=2^20`, one `2^-40` update is retained as expected change and produces error `-2^-40` when storage does not move.
- wide-range limit: at `x_0=2^-20`, 10,000 updates of `2^20` retain the first operation's `-2^-20` error after a large accumulated change.

The model accepts start values in `[2^-20, 2^20]`, updates in `[0, 2^20]`, and integer addition
counts in `[0, 10000]`. The UI narrows those to start exponents `[-2,4]`, update sizes `[0.1,2]`
ULP at one, and `[0,4096]` additions.
